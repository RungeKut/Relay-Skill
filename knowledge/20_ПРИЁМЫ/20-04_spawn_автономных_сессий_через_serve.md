# Автономный воркер через serve

## Механизм

`.relay/agents.json` в проекте:

```json
{"glm": {"cmd": ["node", "<путь>/resources/glm/zcode.cjs", "-p", "{prompt}", "--cwd", "{cwd}"],
         "env": {"ZCODE_DATA_BASE_DIR": "<каталог данных воркера>", "ZCODE_LOG_CONSOLE": "1"},
         "timeout": 14400}}
```

`python relay.py serve --agent glm --poll 2` — постоянный процесс-ждун: берёт
задание из инбокса, создаёт worktree, спавнит headless-сессию `-p`, пишет лог
`.relay/log/<агент>-<id>.log`, переносит задание в `done`; без отчёта —
автоматический `status: fail` с хвостом лога. Токенов не тратит.

## Кто дежурит

`send` не зависит от serve — задание просто ложится в инбокс и ждёт. Кто
поднимает сам serve:

* выбранный вариант: **лид поднимает serve фоновым процессом своего сеанса**
  (одна команда, ноль токенов); дежурство живёт вместе с сеансом лида — сеанс
  закрыт, дежурства нет, накопленные задания заберёт следующий serve;
* вариант запасной: serve в обычном терминале человека или автозапуск —
  живёт независимо от ИИ-сеансов.

Два serve одновременно не конфликтуют: перенос файла из инбокса атомарен,
задание заберёт ровно один. Остановка serve между заданиями безопасна,
во время задания — убивает воркера (см. «Осторожно»).

## Ключевое: изоляция каталога данных

Приложение ZCode и CLI на одной машине пишут токены в один файл
`~/.zcode/v2/credentials.json`: каждый вход затирает чужой набор, и вторая
сторона требует вход заново (поэтому раньше `login` разлогинивал приложение).
Лечение: `ZCODE_DATA_BASE_DIR` на каталог вне домашнего — воркер получает свой
`credentials.json`, свой `provider_config.json` и свой идентификатор
устройства; сервер видит отдельное устройство (как второй компьютер), сессии
не конфликтуют.

Вход воркера — один раз, с той же переменной:
`set ZCODE_DATA_BASE_DIR=<каталог> && node ...zcode.cjs login zai`.
Браузер приложение открывает с обрезанной ссылкой (всё после `&` теряется) —
полную ссылку взять из вывода login и открыть вручную. Модель по умолчанию
login пишет в `provider_config.json` рядом с credentials; дешёвую Flash-модель
прописать там же руками (`defaultModelSelection.modelId`).

## Наблюдаемость

* без `console` — вывод воркера в `.relay/log/<агент>-<id>.log`; `ZCODE_LOG_CONSOLE=1`
  делает его подробным; смотреть: `tail -f` (Git Bash) или `Get-Content -Wait` (PowerShell).
* `"console": true` в agents.json (Windows) — отдельное консольное окно на каждое
  задание с живым выводом; окно закрывается по завершении, отчёт — в `result/`.

## Исследование авторизации (2026-11-04, всё проверено экспериментами)

Почему приложение ZCode работает без перелогинов, а headless-воркер — нет:

* приложение — долго живущий процесс со своей службой: держит живую сессию
  в памяти, сама её обновляет и переживает перезапуск через собственное
  персистентное хранилище (не `credentials.json` — его содержимое при этом
  не меняется);
* свежие авторизационные данные раздаются дочерним рантаймам через IPC
  «provider runtime headers», канал передаётся от родителя к ребёнку при
  запуске; снаружи (из serve) не обнаруживается и не подключается;
* в CLI нет refresh для Z.ai вообще (в бандле refresh-код только от Vercel);
* копия `credentials.json` приложения воркеру не помогает: файловый токен
  отвергается обменником (`/api/auth/z/login` отвечает «user information
  is invalid»), живая сессия приложения в файле не лежит;
* `--surface desktop` не переносит авторизацию на running-приложение;
* план привязывается к воркеру в момент входа; смена плана в приложении
  требует перелогина воркера;
* токен воркера живёт около двух часов, `-p` его не обновляет
  (`credentials.json` не переписывается с момента входа).

## Пути возврата к spawn

1. Появится refresh в CLI Z.ai (новая версия ZCode) — пере проверять `-p`:
   вся схема уже собрана (agents.json, изоляция, console).
2. Появится API-ключ Z.ai/BigModel: конфиг поддерживает встроенного
   провайдера с `options.apiKey` без OAuth и без TTL — тогда воркер без
   логинов вообще и без привязки к плану.
3. Пока нет ни того ни другого — держаться chat-схемы (20-01, 20-03).

## Осторожно

* Ссылка авторизации одноразовая и живёт минуты: протухла — генерировать новую.
* `ZCODE_LOG_CONSOLE=1` до входа не нужен, но не мешает.
* OAuth-токен воркера живёт около двух часов, и одноразовая `-p`-сессия его
  не обновляет (credentials.json не переписывается с момента входа).
  Симптом: все задания подряд падают `project_token_login_failed` на любом
  плане. Лечение — перелогин воркера (изолированный, приложение не
  затрагивает), затем упавшие задания вернуть из `done` в инбокс.
* Воркер следует плану своего входа: после смены плана в приложении
  перелогинить воркера, иначе запросы падают или тратят чужую квоту.
* Остановка serve (или гибель его процесса) убивает и текущего воркера —
  дерево процессов; воркер гибнет без отчёта, задание остаётся в `work/`.
  Останавливать serve можно только между заданиями (heartbeat-файл `work`
  пуст); упавшему без отчёта воркеру дописывают `status: fail` вручную.
* Шаблон `go.md` всё ещё описывает исполнителя-чат с циклом `listen` (20-03);
  при serve чат-исполнителю не требуется — решение о переработке шаблона за владельцем.
